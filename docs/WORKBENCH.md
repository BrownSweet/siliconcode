# 浏览器开发工作台

`brown serve` 是独立 HTTP 服务，复用当前 DeepSeekClient、CacheFirstLoop、ToolRegistry、
文件工具和 PauseGate，不需要启动 Ink 或伪终端。原 `brown code` Dashboard 和旧 delivery
入口保留兼容；浏览器工作台使用独立的账户、项目、需求版本与执行记录。

## 本机启动

要求 Node.js 22+；源码目录先 `npm run build`。

```bash
brown serve --port 3000
```

默认地址为 `http://127.0.0.1:3000`，默认数据目录为 `~/.siliconcode/workbench`，
模型配置沿用 `~/.siliconcode/config.json`。可用 `--data-dir` 和 `--config-path` 覆盖；
同一数据目录只允许一个服务持有写锁。

第一次启动会输出一次性设置凭据；浏览器创建用户名和至少 12 字符的密码后失效。
密码保存为随机盐的 scrypt 派生值，不保存明文。会话使用 HttpOnly、SameSite=Strict Cookie，
12 小时过期。注销、修改密码或服务重启后需要重新登录。修改密码会撤销所有已有会话。
账户密码与模型 API Key 分开配置；API 不回显 Key。

## 项目与版本流程

1. 点击左侧「打开项目文件夹」，浏览、筛选并选择已有目录；也可通过 `⌘/Ctrl+O` 打开。
   macOS 本机服务支持「系统选择器」，直接使用 Finder 文件夹窗口；远程服务使用目录列表。
   路径始终属于运行服务的电脑。项目 ID 绑定规范化目录，文件工具不沿用终端的
   跨目录授权，也拒绝符号链接逃逸。项目目录不能包含工作台账户数据。
2. 点击「新建任务」，填写版本名称和需求后发送，自动创建版本并开始分析；模型可只读项目代码并调用
   `record_requirements` 保存 PRD、SDD、验收项、待澄清问题和测试/打包命令。
3. 通过后续对话回答问题或修订需求。所有草案修订和对话持久化。
4. 没有待澄清问题且已给出测试和打包命令时，用户可以确认当前修订。
   确认动作检查修订号；旧页面不能确认已更新的文档。确认后文档不可原地修改。
5. 勾选授权并开始开发：允许模型按文档编辑当前目录；额外 shell 命令需要逐次审批。
   已确认的测试、打包命令由服务执行，不接受模型自报退出码。
6. 使用新的只读回合进行独立审查，再执行全部验证命令。发现问题最多进行 3 轮开发/修复。
   每轮结果绑定当前代码指纹，后续修改使旧证据失效。Git 子模块暂不支持自动验证。
7. 下一版选择已确认的父版本，例如 `2.0` 基于 `1.0`。父版本文档进入新的需求分析与
   开发上下文，旧修订仍可查看。新增或变更的需求须重新澄清、确认和验证。

草案的 `checks` 是必填数组，命令尚未确定时传 `[]`，不使用 `echo` 或 `true` 充当测试。
验证命令按 argv 解析，支持命令连接和常见重定向，但不自动展开通配符、环境变量或命令替换。
例如包检查应写 `tar -tzf dist/local-todo-2.0.0.tgz`，不能写 `tar -tzf dist/*.tgz`。
已确认命令需要变更时，派生新需求版本重新确认，保留旧任务的失败证据。

页面采用项目侧栏、对话区和可收起详情面板。左侧切换项目与历史版本，底部输入框支持
`⌘/Ctrl+Enter` 发送；右侧「需求 / 设计 / 验收 / 执行结果 / 变更」展示 Markdown 文档、
逐项审查、真实命令输出和彩色差异。头像入口提供模型、外观和账户设置，默认浅色，可切换深色。
窄屏下项目栏折叠，详情面板单独展开。目录浏览仅返回文件夹名称，隐藏账户/密钥/系统目录，
不会上传目录内容；选择项目之后仍需确认文档、授权开发和审批额外命令。

自动开发在所选工作目录直接修改文件，支持普通目录、尚无提交和已有提交的 Git 项目。
任务开始时保存源文件快照，包含已有未提交修改；页面展示相对于该快照的新增、修改和删除。
二进制及大文件仍参与指纹校验，差异正文省略时有明确提示。不会自动初始化 Git、reset、commit、push、发布或部署。
需要隔离工作区时，使用页面顶部「项目工具 → 隔离工作区」。也可自行创建 worktree 后将目录添加为普通项目。

Git 项目依据 Git 的已跟踪和非忽略文件选择验证范围；普通目录遵守各级 `.gitignore`，
另跳过 `.git`、`node_modules`、`.venv`、`venv`、`__pycache__`、`.cache` 目录。
构建输出请明确加入 `.gitignore`。不跟随符号链接读取目标；不支持 Git 子模块，项目最多 50,000 个条目。
快照保存单文件最多 128 KiB、总计最多 4 MiB 的文本用于差异展示，完整文件内容仍参与哈希。

测试或打包若写入非忽略的生成文件，会改变指纹，使本轮审查证据失效。
应先确认生成文件归属与 `.gitignore`，然后重新运行；不得通过删除业务文件消除差异。

## 错误和恢复

- LLM 请求总超时默认 660 秒，流读取空闲超时默认 120 秒；用户取消同时有效。
- 认证/参数错误不盲目重试；临时网络、429/5xx 有限退避。部分内容输出后断流直接报错，
  保留事件，不透明重放工具，也不把半截回答判为成功。
- 每个任务独立审批；审批绑定任务 ID 与请求 ID，过期审批拒绝。刷新页面重新读取任务
  与审批，SSE 使用单调事件序号支持断线续传，断开浏览器不会重新启动任务。
- 大历史按文件快照分段读取并等待 HTTP 发送缓冲释放；实时事件在回放前订阅，按序号去重衔接。
  浏览器关闭后会取消读取并释放订阅。项目活动状态独立于当前查看的历史版本，每 1.5 秒检查变化；
  只有状态发生变化才加载详情，避免切换版本后一直停留在忙碌状态。
- 模型设置显示有效配置的字段来源。`DEEPSEEK_API_KEY` / `DEEPSEEK_BASE_URL` 优先时，
  保存配置文件不会覆盖服务环境；页面明确提示调整环境并重启，不将已保存误报为已生效。
- 停止任务会中断模型请求和命令，撤销等待中的审批，最终状态为 interrupted。
- 模型报错或用户取消后，服务会重新读取工作区并保存相对于开发前快照的差异，已写入的文件不会自动回滚。
  差异显示不代表审查或测试通过。若工作区或快照已不可读，会保留原始错误并提示无法更新差异，避免展示旧差异冒充最终状态。
- 服务重启将进行中的任务标为 interrupted，保留工具记录、文档、审查与命令证据。
  用户核对实际文件后点击继续；新任务关联上次失败/中断任务，带入错误、命令结果和最近工具回执，
  先检查当前代码，再生成新的审查和测试证据。只有开始记录而没有完成回执的命令不能视为成功，
  不会自动重放；旧任务的证据保留，可从新任务返回查看。
- 单条验证命令超时为文档里的 1–600 秒，输出最多保存 64,000 字符。
- 各阶段使用浏览器专用提示词，工具名来自实际注册列表，不沿用终端的计划、技能或后台任务调用说明。
  需求分析、开发和审查都会读取工作目录根部的项目规则（`AGENTS.md` 优先于 `SILICON.md`，
  兼容旧规则文件名）；规则文件不能通过符号链接指向项目外。根规则最多自动载入 8,000 字符，
  超长时提示模型按需继续读取；子目录规则由模型在进入目录时通过只读工具检查。

## 远程访问与边界

这是个人管理员工作台，不是多租户执行沙箱。模型文件工具有项目路径限制；
经批准的 shell、项目测试和构建脚本仍拥有服务进程的系统用户权限。
仅在可信项目中运行；不同系统用户/容器权限隔离不由账户字段提供。

远程监听必须配置 HTTPS 反向代理和外部 origin，例如：

```bash
brown serve --host 0.0.0.0 --port 3000 --origin https://code.example.com
```

代理须保留外部 Host、支持 SSE、关闭事件流缓冲；把后端端口限制在代理可访问的网络，
不要直接公开 HTTP 端口。HTTPS origin 使用 Secure Cookie；服务校验 Host、Origin、CSRF。

旧 delivery 流程的 production approval 仍是同一系统用户可写的本地状态，不能抵御
拥有任意 shell 权限的自动化进程自改状态。浏览器工作台不提供生产部署入口，不能把本地
任务完成解释成生产发布成功。

## 日常使用与备份

- 输入草稿按账户、项目和需求版本保存在当前浏览器，输入时写入；刷新后恢复上次视图。
  同一项目的新任务入口恢复未发送草稿；创建升级草稿也不会静默覆盖已有正文。
  浏览器存储失败时会提示先复制正文。草稿不随服务端备份导出。
- 「管理任务」可改显示名称、归档和恢复。原始需求、确认文档与执行记录保持原样；
  已归档任务须先恢复才能继续执行。项目侧栏可搜索任务及查看归档。
- 「设置 → 运行限制」配置下一次任务的 Token 和估算美元费用上限，涵盖开发、审查和修复。
  每次模型响应后核验，到达上限后不再执行后续工具或模型请求；单次请求可能超过剩余额度。
  缺失用量或价格不能记作零，设置相应上限时将停止任务，保留已有修改和证据。
- 「设置 → 模型 → 检查当前连接」复用有效凭据读取模型列表，不发送项目内容，也不自动切换模型。
  列表可访问不等同于推理请求已验证。
- 「设置 → 数据」导出 `.scwb.gz` 备份，格式版本 1，逐文件 SHA-256 校验。
  包含账户密码哈希、需求对话、执行日志和快照；不包含完整项目目录、模型配置和浏览器草稿。
  任务执行期间不能导出；导出期间暂时禁止数据修改。备份限 1 GiB 原始记录。
- 恢复只接受空目录，先在临时目录校验完整性、文件名与格式，再发布恢复结果。
  不恢复进程锁，不自动运行历史任务。原项目路径若已变化，需重新添加实际工作目录。

```bash
brown workbench-restore /path/backup.scwb.gz --data-dir /path/new-workbench
brown serve --data-dir /path/new-workbench --port 3000
```

## 隔离工作区、合并与预览

「项目工具 → 隔离工作区」从 Git 仓库根目录的当前提交创建 `codex/workbench-*`
分支和相邻 `.siliconcode-worktrees/` 下的独立目录，并作为新项目打开。已有的未提交修改、
忽略文件及依赖不复制；需求、任务和授权属于新项目。原项目必须有提交且已切换到命名分支。
普通目录与无提交 Git 目录继续直接开发，不会自动初始化 Git。

在隔离项目查看当前全部差异后，可以勾选授权合并。差异包含新增、修改、删除和二进制变更标记；
忽略文件不纳入，子模块和嵌套 Git 仓库拒绝合并。预览 diff 超过 8 MiB 时请求失败，不截断后继续合并。
服务用临时 Git index 生成待审树，不改变用户的暂存区。
合并重新核对树哈希、原分支和 HEAD；原目录有未提交内容、已前进或已换分支时拒绝。
完成后保存一个提交并快进合并，结果分支、隔离目录、暂存状态和任务记录均保留。
每个隔离项目只提供一次自动合并；继续迭代请从原项目另建隔离工作区。

合并只执行 Git 保存和快进操作，不执行 Git hooks、不自动重跑验证，也不替用户解决冲突。
用户可在 Git 中审查结果提交，并通过 `git revert <合并结果提交>` 创建反向提交；工作台不执行 reset。
模型阶段的完成证据属于当时的文件快照，手工改动后应先重新验证再合并。

「项目工具 → 预览与日志」填写项目已有的启动命令和本机 URL，勾选授权后执行。
命令使用 argv，不支持 shell 管道/连接；需要组合步骤时用项目脚本。建议命令显式绑定 127.0.0.1。
URL 仅允许本机 HTTP(S) 地址且不得含用户名密码；不会自动探测网页或将预览代理到公网。
远程工作台不提供会指向浏览器本机的打开链接，需要用户已有的安全端口转发。
预览进程与相关目录中的开发任务互斥；查看工作区差异和合并前也需停止预览。
日志保留最近约 64 KiB；进程状态、退出码和启动失败原因可查看。
停止及服务正常退出会清理所管理的进程树，重启不自动重放预览命令。
强制杀死服务进程/系统断电不属于可执行退出清理的情形。

工作台与旧 delivery 页面使用同一执行结果摘要组件，但保留各自执行器和证据。
本地完成要求同一文件指纹的审查、测试、打包回执；需求分析完成不表示代码验收。
delivery 依据当前迭代、阶段关联的证据分别展示验收、审批、预发布、金丝雀与观察期，
不将审批通过当作部署成功，也不将历史健康记录当作此刻线上健康。

在容器日志中读取首次管理员设置凭据，登录后打开挂载目录 `/workspace/project`。
账号、项目与需求版本保存在 `/home/node/.siliconcode/workbench`，随状态数据卷持久化。
